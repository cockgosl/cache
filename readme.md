# Cache Simulator

Проект представляет собой симулятор многоуровневого кэша, реализованный на C++.

В проекте реализованы пять алгоритмов кэширования:

- **LRU** — Least Recently Used;
- **LFU** — Least Frequently Used;
- **2Q** — Two Queues;
- **ARC** — Adaptive Replacement Cache;
- **LIRS** — Low Inter-reference Recency Set.

Для всех алгоритмов используется общий интерфейс кэша, благодаря чему для каждого уровня можно независимо выбрать алгоритм.

Проект поддерживает две организации многоуровневого кэша:

- **Exclusive cache** — страница физически находится только на одном уровне;
- **Inclusive cache** — страница, находящаяся на верхнем уровне, также присутствует на всех нижних уровнях.

Также проект содержит автоматические тесты на **Google Test**.

---

# Алгоритмы кэширования

## LRU

**Least Recently Used**

Удаляет страницу, которая дольше всего не использовалась.

## LFU

**Least Frequently Used**

Удаляет страницу с наименьшей частотой обращений.

## 2Q

**Two Queues**

Использует две очереди для разделения страниц в зависимости от характера обращений к ним.

## ARC

**Adaptive Replacement Cache**

Адаптивно балансирует между недавно использованными и часто используемыми страницами.

## LIRS

**Low Inter-reference Recency Set**

Использует интервал между обращениями к страницам для определения того, какие страницы следует сохранять в кэше.

# Многоуровневый кэш

Проект поддерживает иерархию из нескольких уровней кэша.

Например:

```text
+------+
|  L1  |
+--+---+
   |
   v
+------+
|  L2  |
+--+---+
   |
   v
+------+
|  L3  |
+--+---+
   |
   v
Slow storage
```

Для каждого уровня можно независимо задать:

- алгоритм замещения;
- вместимость.

Например:

```text
L1 = LRU, capacity 100
L2 = LFU, capacity 500
L3 = ARC, capacity 1000
```

Благодаря общему интерфейсу кэша разные алгоритмы могут использоваться одновременно в одной иерархии.

Например:

```text
L1 = LRU
L2 = LFU
L3 = ARC
```

или:

```text
L1 = 2Q
L2 = ARC
L3 = LIRS
```

# Exclusive Cache

Основная исходная организация проекта — **exclusive cache**.

В exclusive-кэше одна страница физически находится только на одном уровне.

То есть одна и та же страница не должна одновременно находиться в `L1`, `L2` и `L3`.

## Обработка запроса

Для каждого запроса уровни проверяются последовательно:

```text
Request
   |
   v
  L1
   |
 miss
   v
  L2
   |
 miss
   v
  L3
   |
 miss
   v
Slow storage
```

Если страница найдена в `L1`, запрос считается попаданием.

Если страница найдена, например, в `L2`, она удаляется из `L2` и перемещается в `L1`:

```text
L1: miss
 |
 v
L2: hit
 |
 v
page -> L1
```

Если при вставке страницы в `L1` происходит вытеснение другой страницы, вытесненная страница передаётся на следующий уровень:

```text
L1 -> L2 -> L3
```

Если `L3` также переполнен, вытесненная из него страница удаляется из кэш-системы.

Основное свойство exclusive-организации:

> Одна страница находится не более чем на одном уровне кэша.

Это позволяет использовать суммарную вместимость всех уровней без хранения дублирующихся копий страниц.

---

# Inclusive Cache

Проект также поддерживает **inclusive cache**.

В отличие от exclusive-организации, в inclusive-кэше одна и та же страница может одновременно находиться на нескольких уровнях.

Основной инвариант:

```text
L1 ⊆ L2 ⊆ L3
```

То есть каждая страница, находящаяся в `L1`, должна также присутствовать в `L2` и `L3`.

Например:

```text
L1: {1, 2}
L2: {1, 2, 3}
L3: {1, 2, 3, 4}
```

## Загрузка страницы

Если страницы нет ни на одном уровне, она загружается из медленного хранилища и помещается на каждый уровень:

```text
Request: 5

L1: {5}
L2: {5}
L3: {5}
```

Таким образом, после полной загрузки выполняется:

```text
L1 ⊆ L2 ⊆ L3
```

## Попадание на нижнем уровне

Если страница найдена, например, в `L2`, она остаётся в `L2` и также должна присутствовать на верхних уровнях.

Например:

```text
До:

L1: {2}
L2: {1, 2, 3}

Request: 3

После:

L1: {3, 2}
L2: {1, 2, 3}
```

В отличие от exclusive-кэша, страница не удаляется из `L2`.

Она остаётся на нижнем уровне и одновременно появляется на верхнем.

## Вытеснение

В inclusive-кэше особенно важно правильно обрабатывать вытеснение на нижних уровнях.

Если страница удаляется из `L2`, её копия в `L1` также должна быть удалена.

Например:

```text
До:

L1: {1, 2}
L2: {1, 2, 3}
```

Если `1` вытеснена из `L2`:

```text
L1: {2}
L2: {2, 3}
```

Копия `1` в `L1` должна быть инвалидирована.

Это необходимо для сохранения инварианта:

```text
L1 ⊆ L2
```

Аналогично, если страница вытесняется из `L3`, её копии должны быть удалены из всех верхних уровней.

---

# Медленное хранилище

Если страница отсутствует на всех уровнях кэша, запрос доходит до медленного хранилища.

Для каждой страницы сохраняется её значение.

Поэтому при повторном обращении к тому же ключу из медленного хранилища возвращается то же значение.

Это позволяет моделировать работу кэша без использования реальной системы памяти.

# Статистика

Для каждого уровня кэша подсчитываются:

- `Hits` — количество попаданий;
- `Misses` — количество промахов.

Пример:

```text
L1:
    Hits: 100
    Misses: 900

L2:
    Hits: 300
    Misses: 600

L3:
    Hits: 200
    Misses: 400
```

Для многоуровневого exclusive-кэша промах на одном уровне означает, что поиск продолжается на следующем уровне.

Поэтому:

```text
L2 requests = L1 misses
```

и:

```text
L3 requests = L2 misses
```

# Входные данные

Программа получает конфигурацию многоуровневого кэша и последовательность обращений к страницам из входного файла.

## Формат входного файла

```text
N
algorithm_1 capacity_1
algorithm_2 capacity_2
...
algorithm_N capacity_N

page_1 page_2 page_3 ...
```

где:

- `N` — количество уровней кэша;
- `algorithm_i` — алгоритм, используемый на `i`-м уровне;
- `capacity_i` — вместимость `i`-го уровня;
- `page_i` — номер страницы, к которой происходит обращение.

## Доступные алгоритмы

Для указания алгоритма используются:

```text
lru
lfu
2q
arc
lirs
```

## Пример входного файла

```text
3
lru 3
lru 4
lru 5

1 2 3 4 5 2 1 6 7 3 4 2 1 5 6 7 8
```

В данном примере создаются три уровня:

```text
L1: LRU — capacity 3
L2: LRU — capacity 4
L3: LRU — capacity 5
```

После конфигурации уровней располагается последовательность обращений к страницам.

# Обработка запросов

## Exclusive

Для exclusive-кэша при полном промахе:

```text
L1: miss
 |
 v
L2: miss
 |
 v
L3: miss
 |
 v
Slow storage
```

Полученная страница помещается в `L1`.

При переполнении уровней вытесненные страницы перемещаются вниз:

```text
L1 -> L2 -> L3
```

## Inclusive

Для inclusive-кэша при полном промахе страница помещается на все уровни:

```text
L1 <- page
L2 <- page
L3 <- page
```

При попадании на нижнем уровне страница остаётся там и копируется на верхние уровни.

При вытеснении на нижнем уровне соответствующие копии на верхних уровнях инвалидируются.

# Тестирование

Для автоматического тестирования проекта используется **Google Test**.

Тесты находятся в директории:

```text
tests/
```

Тесты проверяют как отдельные алгоритмы кэширования, так и многоуровневую систему.

## Запуск всех тестов

Для сборки и запуска полного набора тестов:

```bash
make test
```

После запуска Google Test выводит количество пройденных и проваленных тестов.

Пример:

```text
[==========] Running all tests
[  PASSED  ] ...
```

## Запуск тестов с фильтром

Makefile поддерживает фильтры Google Test.

Например, чтобы запустить только тесты inclusive-кэша:

```bash
make test-filter FILTER=MultiCacheInclusive.*
```

## Запуск одного теста

Можно запустить конкретный тест:

```bash
make test-filter FILTER=MultiCacheInclusive.MissLoadsPageIntoAllLevels
```

## Что проверяется

Тесты многоуровневого кэша проверяют основные свойства его работы.

Для exclusive-кэша проверяются:

- загрузка страницы после полного промаха;
- перемещение страниц между уровнями;
- передача вытесненных страниц на следующие уровни;
- работа с несколькими уровнями.

Для inclusive-кэша проверяются:

- загрузка страницы после полного промаха на все уровни;
- попадание при поиске на нижнем уровне;
- продвижение страницы на верхний уровень;
- сохранение страницы на нижнем уровне после попадания;
- инвалидирование копий на верхних уровнях после вытеснения страницы с нижнего уровня;
- работа иерархии на последовательностях запросов.

# Воспроизведение исследования

В директории `benchmarks/` находится исследование поведения алгоритмов кэширования на различных типах нагрузок.

Исследование сравнивает:

- LRU;
- LFU;
- 2Q;
- ARC;
- LIRS.

Для каждого алгоритма измеряются:

- количество попаданий (`Hits`);
- доля попаданий (`Hit Ratio`);
- количество попаданий идеального алгоритма Белади (`Ideal Hits`);
- эффективность относительно идеального алгоритма (`Efficiency`).

Для многоуровневого кэша дополнительно сравниваются:

- exclusive-организация;
- inclusive-организация;
- количество попаданий;
- доля попаданий;
- количество обращений к памяти.

## Запуск исследования

Для запуска benchmark необходимо находиться в корневой директории проекта.

Сначала рекомендуется удалить предыдущие результаты сборки:

```bash
make clean
```

Затем собрать и запустить benchmark:

```bash
make benchmark
```

После выполнения результаты будут записаны в:

```text
benchmarks/benchmarks.md
```

Каждый новый запуск перезаписывает этот файл.

## Параметры эксперимента

Все параметры эксперимента задаются непосредственно в `benchmarks/benchmark.cpp`.

Текущая конфигурация:

- количество запросов для каждого workload — `5000`;
- вместимость одиночного кэша — `30`;
- вместимость L1 многоуровневого кэша — `10`;
- вместимость L2 многоуровневого кэша — `20`.

Используются следующие workloads.

### LOOP

Циклическое обращение к рабочему набору из `35` страниц:

```text
0 1 2 ... 34 0 1 2 ... 34 ...
```

Количество запросов — `5000`.

### SCAN

Последовательное обращение к `5000` различным страницам.

Каждая страница запрашивается один раз.

### HOT/COLD

Используется:

- `15` горячих страниц;
- `500` холодных страниц;
- вероятность обращения к горячей группе — `0.85`.

Генератор использует фиксированный seed `42`.

### WORKING_SET

Рабочий набор содержит `25` страниц.

Каждые `250` запросов рабочий набор смещается на половину его размера.

Генератор использует фиксированный seed `42`.

### MIXED

Содержит несколько фаз с различными типами обращений:

- циклический рабочий набор;
- hot/cold-поведение;
- случайные обращения.

Генератор использует фиксированный seed `42`.

### RANDOM

Случайные обращения к страницам в диапазоне `1..150`.

Используется фиксированный seed:

```text
42
```

Таким образом, последовательность запросов воспроизводится между запусками.

## Идеальный алгоритм

Для каждого workload дополнительно вычисляется результат идеального алгоритма Белади (`Belady's OPT`).

Он знает всю последовательность запросов заранее и при вытеснении удаляет страницу, следующее обращение к которой произойдёт позже всего.

Полученный результат используется как теоретическая точка сравнения.

# Архитектура многоуровневого кэша

Каждый уровень использует общий интерфейс кэша.

Это позволяет строить различные конфигурации:

```text
L1 = LRU
L2 = LFU
L3 = ARC
```

или:

```text
L1 = 2Q
L2 = ARC
L3 = LIRS
```

В зависимости от выбранной организации кэша страницы обрабатываются по разным правилам.

## Exclusive

```text
       +------+
       |  L1  |
       +--+---+
          |
       eviction
          |
          v
       +------+
       |  L2  |
       +--+---+
          |
       eviction
          |
          v
       +------+
       |  L3  |
       +--+---+
          |
       eviction
          |
          v
     Slow storage
```

Страница физически находится только на одном уровне.

## Inclusive

```text
       +------+
       |  L1  |
       +--+---+
          |
          | copy
          v
       +------+
       |  L2  |
       +--+---+
          |
          | copy
          v
       +------+
       |  L3  |
       +------+
```

Страница из верхнего уровня также присутствует на нижних уровнях.

Основной инвариант:

```text
L1 ⊆ L2 ⊆ L3
```

При удалении страницы с нижнего уровня её копии на верхних уровнях инвалидируются.
